A Small Site, on Purpose

This site is a few HTML files, one stylesheet, a small JavaScript file, and a folder of images. There is no framework, no database, and no build step. That is not a limitation. It is the design.

I wanted a personal site that could survive a busy school year. Something I could open, edit, and publish without remembering a toolchain. Something that loads fast on a phone and still looks like a place I want to spend time in.

What “static” buys

  • Longevity. HTML from 2026 will still render in 2036.
  • Speed. No server rendering, no client hydration, no waiting for a runtime.
  • Low maintenance. The only dependencies are the files themselves.
  • Portability. GitHub Pages can serve it for free; any static host can replace it.

What I gave up

No comments, no analytics, no content management system. I do not need them yet. If I want a comment section, I can add one later. If I want analytics, I can choose a privacy-friendly tool. Starting without them keeps the site honest.

Fresh HTML

One small problem with static hosting is caching. GitHub Pages does not let me set custom cache headers. A visitor can see an old page after I publish a new one.

So the site does three things. It asks the browser not to cache HTML. It checks a tiny build.json file on every load and reloads once if the deployed version is newer. And a service worker serves page navigations network-first. The goal is simple: when I change something, the change shows up.

Maintenance is a design constraint

A website is a small promise that the thing will still be there. The best way to keep that promise is to make the site easy to repair. Plain files are easy to repair.

This is not an argument against frameworks. They are the right tool for many jobs. It is an argument for choosing the smallest tool that can carry the idea.

For a personal site, the idea is the writing. Everything else should get out of the way.
